# 회원가입 페이지 설계

## 개요

이메일로 가입하는 사용자의 계정 정보, 업종, 약관 동의를 한 화면에서 받는다. 라우트는 `/signup`이다. Figma에 약관 영역 디자인이 없어 기존 입력창·모달 스타일에 맞춰 구성했다.

## 화면 구성

| 영역      | 구성                                                             |
| --------- | ---------------------------------------------------------------- |
| 계정 정보 | 이름, 이메일, 비밀번호, 비밀번호 확인 (`AuthField`)              |
| 업종      | `AuthBusinessTypeField`                                          |
| 약관 동의 | `TermsAgreement`                                                 |
| 액션      | 회원가입 하기, 로그인 이동 링크                                  |
| 소셜 가입 | `AuthSocialLogin` — 이후 흐름은 [onboarding.md](./onboarding.md) |

업종은 계정 정보와 같은 입력 묶음에 두고, 약관 동의는 입력 묶음과 버튼 사이에 둔다.

## 상태·데이터

| 상태        | 범위         | 도구            |
| ----------- | ------------ | --------------- |
| 입력값 전체 | `SignupForm` | React Hook Form |

API 연동 전까지 제출은 이동만 한다. 업종 값은 [README](./README.md#업종) 참고.

## API

| 순서 | 동작      | BE API                   | BFF                                                          |
| ---- | --------- | ------------------------ | ------------------------------------------------------------ |
| 1    | 약관 목록 | `GET /api/terms`         | 범용 통과. 토큰 불필요                                       |
| 2    | 가입      | `POST /api/users/signup` | 범용 통과. 토큰 불필요, 응답에도 토큰이 없다                 |
| 3    | 이동      | —                        | 가입에 성공하면 `/login`으로 이동해 사용자가 직접 로그인한다 |

- 가입 응답에 토큰이 없어 가입만으로는 로그인 상태가 되지 않는다. 자동 로그인 대신 로그인 페이지로 보낸다.
- 요청 body와 응답은 orval이 생성한 요청 함수·zod 스키마를 쓴다.

### 요청 필드

| 필드             | 규칙                                                                   | 폼 필드              |
| ---------------- | ---------------------------------------------------------------------- | -------------------- |
| `email`          | 이메일 형식. 대소문자를 구분하지 않고 소문자로 저장된다                | 이메일               |
| `password`       | 8~20자, 영문과 숫자를 각각 1자 이상, 공백 불가                         | 비밀번호             |
| `name`           | 1~20자                                                                 | 이름                 |
| `industry`       | 업종 enum                                                              | 업종                 |
| `industryDetail` | `industry`가 `CUSTOM`일 때만 보낸다(최대 20자). 그 외에 보내면 400     | `businessTypeCustom` |
| `termsAgreed`    | `GET /api/terms`의 약관 **전체**에 대해 `{ termsId, agreed }`를 보낸다 | `terms`              |

- 비밀번호 확인은 폼에서만 검사하고 보내지 않는다.
- 필수 약관을 `false`로 보내거나 목록에서 빠뜨리면 400 `REQUIRED_TERMS_NOT_AGREED`이고 계정이 만들어지지 않는다.
- 약관 목록(현재): 필수 1~4(만 19세 이상 사업자, 서비스 이용약관, 개인정보 수집·이용, 근로자 개인정보 처리 위탁 특약), 선택 5(마케팅 정보 수신). 화면은 하드코딩하지 않고 `GET /api/terms` 결과로 그린다.

### 실패

| status | errorCode                   | 처리                 |
| ------ | --------------------------- | -------------------- |
| 400    | `INVALID_EMAIL_FORMAT`      | 이메일 필드 인라인   |
| 400    | `INVALID_PASSWORD_FORMAT`   | 비밀번호 필드 인라인 |
| 400    | `INVALID_INDUSTRY_VALUE`    | 업종 필드 인라인     |
| 400    | `REQUIRED_TERMS_NOT_AGREED` | 약관 영역 인라인     |
| 409    | `EMAIL_ALREADY_EXISTS`      | 이메일 필드 인라인   |

- 형식 검사는 폼에서도 같은 규칙으로 먼저 한다. 위 400은 폼 검사를 통과했는데 BE에서 거부된 경우에 대비한다.

## 렌더링 경계

`page.tsx`는 Server Component로 레이아웃과 메타데이터만 담당한다. 폼 상태와 라우터 이동이 필요한 `SignupForm`부터 Client Component다.

## 설계 결정

| 결정                 | 선택                                               | 근거                                                   |
| -------------------- | -------------------------------------------------- | ------------------------------------------------------ |
| 약관 전문 노출       | 모달                                               | 본문이 길어 페이지에 펼치면 가입 폼이 밀려난다         |
| 약관 요약 노출       | 페이지에는 체크 항목만, 수집 항목 요약은 모달 상단 | 400px 폭에서 요약까지 펼치면 버튼이 화면 밖으로 밀린다 |
| 전문 보기 → 동의하기 | 해당 항목 자동 체크                                | 전문을 읽은 뒤 다시 체크박스를 찾지 않도록 한다        |

## 확인 필요

[README의 확인 필요](./README.md#확인-필요) 참고. 가입 API와 관련해 추가로 확인할 것은 아래와 같다.

1. **업종 enum 불일치** — BE 명세 설명 문장은 `RETAIL`·`BEAUTY`·`ACADEMY`를 말하지만, 스키마 enum과 생성 zod는 `RESTAURANT`·`CAFE`·`BAKERY`·`PUB`·`CONVENIENCE_STORE`·`CUSTOM`이다. 화면은 스키마 enum을 따르고, 설명 문장은 BE에 수정을 요청한다.
2. **마케팅 수신 항목** — BE 약관은 마케팅 수신 동의가 하나(id 5)인데, 화면의 약관 체크 규칙은 이메일·SMS 두 수단으로 나뉜다([README](./README.md#약관-체크-규칙)). 화면을 하나로 합칠지, 두 체크를 id 5 하나로 보낼지 정한다.
