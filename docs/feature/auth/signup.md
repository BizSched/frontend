# 회원가입 페이지 설계

## 개요

이메일로 가입하는 사용자의 계정 정보, 업종, 약관 동의를 한 화면에서 받는다. 라우트는 `/signup`이다. Figma에 약관 영역 디자인이 없어 기존 입력창·모달 스타일에 맞춰 구성했다.

## 화면 구성

| 영역      | 구성                                                             |
| --------- | ---------------------------------------------------------------- |
| 계정 정보 | 이름, 이메일, 비밀번호, 비밀번호 확인 (`AuthField`)              |
| 업종      | `AuthBusinessTypeField`                                          |
| 약관 동의 | `TermsAgreement` — 약관 목록은 `GET /api/terms` 결과로 그린다    |
| 액션      | 가입 실패 문구, 회원가입 하기, 로그인 이동 링크                  |
| 소셜 가입 | `AuthSocialLogin` — 이후 흐름은 [onboarding.md](./onboarding.md) |

업종은 계정 정보와 같은 입력 묶음에 두고, 약관 동의는 입력 묶음과 버튼 사이에 둔다.

## 상태·데이터

| 상태        | 범위             | 도구                                | 근거                                                          |
| ----------- | ---------------- | ----------------------------------- | ------------------------------------------------------------- |
| 입력값 전체 | `SignupForm`     | React Hook Form (`rules`)           | 폼 상태 규칙. 형식 검사는 BE와 같은 규칙으로 폼에서 먼저 한다 |
| 약관 목록   | `TermsAgreement` | `useQuery` (`termsQueryOptions`)    | 서버 데이터. 서버에서 prefetch해 첫 화면에 바로 보인다        |
| 가입 요청   | `SignupForm`     | `useMutation` (`useSignupMutation`) | 변경 요청                                                     |

- 가입은 mutation이라 `throwOnError`를 쓰지 않고 `onError`에서 처리한다([error-handling.md](../../architecture/error-handling.md)).
- 가입에 성공하면 `/login`으로 이동한다. 가입 응답에 토큰이 없어 사용자가 직접 로그인한다.
- 가입 요청 중과 성공 후 이동 전에는 입력·업종·약관 조작을 잠근다. 실패하면 다시 편집할 수 있다.
- 업종 값은 [README](./README.md#업종) 참고.

### 입력 검사

| 필드          | 규칙                                           | 문구                                                         |
| ------------- | ---------------------------------------------- | ------------------------------------------------------------ |
| 이름          | 필수                                           | 이름을 입력해주세요.                                         |
| 이름          | 20자 이하                                      | 이름은 20자 이하로 입력해주세요.                             |
| 이메일        | 필수                                           | 이메일을 입력해주세요.                                       |
| 이메일        | 로그인과 같은 형식 규칙                        | 올바른 이메일 형식이 아닙니다.                               |
| 비밀번호      | 필수                                           | 비밀번호를 입력해주세요.                                     |
| 비밀번호      | 8~20자, 영문과 숫자를 각각 1자 이상, 공백 불가 | 비밀번호는 공백 없이 8~20자의 영문과 숫자를 포함해야 합니다. |
| 비밀번호 확인 | 필수                                           | 비밀번호를 한 번 더 입력해주세요.                            |
| 비밀번호 확인 | 비밀번호와 같음                                | 비밀번호가 일치하지 않습니다.                                |
| 업종          | 선택 필수                                      | 업종을 선택해주세요.                                         |
| 직접 입력     | `CUSTOM`일 때 필수                             | 업종을 입력해주세요.                                         |
| 직접 입력     | 20자 이하                                      | 업종은 20자 이하로 입력해주세요.                             |
| 약관          | 필수 약관(`required: true`)에 모두 동의        | 필수 약관에 모두 동의해주세요.                               |

- 제출 버튼은 항상 누를 수 있고, 제출하면 빠지거나 틀린 항목 아래에 문구를 보여준다. 약관 문구는 약관 영역 아래 한 줄로 보여준다([README](./README.md#필수-항목-검증)).
- 이메일 형식 규칙은 로그인과 공통 함수로 둔다. 가입할 수 있는 이메일이면 로그인 폼도 통과해야 하기 때문이다.

## API

| 순서 | 동작      | BE API                   | BFF                                                          |
| ---- | --------- | ------------------------ | ------------------------------------------------------------ |
| 1    | 약관 목록 | `GET /api/terms`         | 범용 통과. 토큰 불필요                                       |
| 2    | 가입      | `POST /api/users/signup` | 범용 통과. 토큰 불필요, 응답에도 토큰이 없다                 |
| 3    | 이동      | —                        | 가입에 성공하면 `/login`으로 이동해 사용자가 직접 로그인한다 |

- 가입 응답에 토큰이 없어 가입만으로는 로그인 상태가 되지 않는다. 자동 로그인 대신 로그인 페이지로 보낸다.
- 요청 body와 응답은 orval이 생성한 요청 함수·zod 스키마를 쓴다.

### 약관 목록

- `page.tsx`가 서버에서 `termsQueryOptions`로 prefetch하고 `HydrationBoundary`로 넘긴다([rendering.md](../../architecture/rendering.md)의 "하이브리드 데이터 패칭"). 서버 요청은 `next: { revalidate: 3600 }`으로 1시간 캐시한다. 약관은 모든 사용자에게 같은 공개 데이터다.
- 체크 항목 문구는 약관 `title`, 필수·선택 표시는 `required`, 전문은 `content`로 그린다. 순서는 BE 응답을 따른다.
- 조회에 실패하면 약관 영역에 "약관을 불러오지 못했어요."와 "다시 불러오기" 버튼을 보여주고, 약관을 불러올 때까지 회원가입 버튼을 비활성화한다. 약관 없이는 `termsAgreed`를 만들 수 없다.
- 가입 요청이 `REQUIRED_TERMS_NOT_AGREED`로 거부되면 약관 목록을 다시 조회한다. 재조회 중에는 약관 조작과 가입 제출을 막고, 기존 동의는 유지하며 새 필수 항목에 동의하도록 안내한다. 재조회에 실패하면 같은 재시도 UI로 복구한다.

### 요청 필드

| 필드             | 규칙                                                                                                 | 폼 필드              |
| ---------------- | ---------------------------------------------------------------------------------------------------- | -------------------- |
| `email`          | 이메일 형식. 대소문자를 구분하지 않고 소문자로 저장된다                                              | 이메일               |
| `password`       | 8~20자, 영문과 숫자를 각각 1자 이상, 공백 불가                                                       | 비밀번호             |
| `name`           | 1~20자                                                                                               | 이름                 |
| `industry`       | `RESTAURANT`·`CAFE`·`BAKERY`·`PUB`·`CONVENIENCE_STORE`·`CUSTOM` 중 하나 ([README](./README.md#업종)) | 업종                 |
| `industryDetail` | `industry`가 `CUSTOM`일 때 필수(최대 20자). 그 외에 보내면 400                                       | `businessTypeCustom` |
| `termsAgreed`    | `GET /api/terms`의 약관 **전체**에 대해 `{ termsId, agreed }`를 보낸다                               | `terms`              |

- 비밀번호 확인은 폼에서만 검사하고 보내지 않는다.
- 약관을 목록에서 빠뜨리면 동의하지 않은 것으로 본다. 필수 약관을 `false`로 보내거나 빠뜨리면 400 `REQUIRED_TERMS_NOT_AGREED`이고 계정이 만들어지지 않는다. 선택 약관의 `false`도 미동의로 기록되므로, 화면에 보인 약관 전체를 `true`/`false`로 보낸다.
- 생성 zod 스키마(`SignupBody`)에는 타입만 있고 길이·형식 규칙이 없다. 형식 검사는 "입력 검사"의 폼 규칙으로 한다.
- 가입 응답(`SignupResponse`: `id`, `name`, `email`, `industry`, `industryDetail`, `createdAt`)은 생성 zod로 검증만 하고 화면에서 쓰지 않는다.

### 실패

| status         | errorCode                   | 표시 위치            | 문구                              |
| -------------- | --------------------------- | -------------------- | --------------------------------- |
| 409            | `EMAIL_ALREADY_EXISTS`      | 이메일 필드 인라인   | 이미 가입된 이메일입니다.         |
| 400            | `INVALID_EMAIL_FORMAT`      | 이메일 필드 인라인   | 입력 검사의 이메일 형식 문구      |
| 400            | `INVALID_PASSWORD_FORMAT`   | 비밀번호 필드 인라인 | 입력 검사의 비밀번호 형식 문구    |
| 400            | `INVALID_INDUSTRY_VALUE`    | 업종 필드 인라인     | 업종을 다시 선택해주세요.         |
| 400            | `REQUIRED_TERMS_NOT_AGREED` | 약관 영역 인라인     | 입력 검사의 약관 문구             |
| 400            | 그 밖의 코드                | 토스트               | BE `message`(`formatCommonError`) |
| 5xx · 네트워크 | —                           | 토스트               | 공통 문구(`formatCommonError`)    |

- 400은 폼 검사를 통과했는데 BE에서 거부된 경우에 대비한다. BE 명세에 정의된 가입 실패 코드는 위 5개다. 이름·직접 입력 업종 규칙 위반의 코드는 명세에 없어, 폼 검사로 막고 BE가 거부하면 BE `message`를 보여준다.
- 필드에 연결되지 않는 실패는 로그인 폼과 같이 토스트로 알린다([login.md](./login.md)).

## 렌더링 경계

`page.tsx`는 Server Component로 레이아웃, 메타데이터, 약관 목록 prefetch를 담당한다. 폼 상태와 라우터 이동이 필요한 `SignupForm`부터 Client Component다.

## 설계 결정

| 결정                 | 선택                                                  | 근거                                                                                |
| -------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 약관 전문 노출       | 모달                                                  | 본문이 길어 페이지에 펼치면 가입 폼이 밀려난다                                      |
| 약관 본문 노출       | 페이지에는 체크 항목만, 모달에는 API의 `content` 표시 | API에 요약 필드가 없어 별도 요약을 하드코딩하지 않는다                              |
| 전문 보기 → 동의하기 | 해당 항목 자동 체크                                   | 전문을 읽은 뒤 다시 체크박스를 찾지 않도록 한다                                     |
| 약관 목록·본문 출처  | `GET /api/terms`                                      | 약관 개정을 BE에서 한 번에 반영한다. FE에 본문을 두면 두 곳을 함께 고쳐야 한다      |
| 마케팅 수신 동의     | 체크 하나(약관 id 5)                                  | BE 약관이 수신 수단을 나누지 않는다. 수단별 설정은 알림 설정에서 한다               |
| 필수 항목 검증       | 제출 시 인라인 문구                                   | 폼이 길어 버튼 비활성만으로는 무엇이 빠졌는지 알 수 없다. 로그인 폼과 같은 방식이다 |
| 약관 조회 시점       | 서버 prefetch, 1시간 캐시                             | 첫 화면에 로딩 없이 보인다. 약관은 자주 바뀌지 않는 공개 데이터다                   |

- 2단계는 `dev`에서 분기한다. 3단계부터는 바로 앞 단계 브랜치에서 분기한 stacked PR이고, 앞 단계가 머지되면 base를 `dev`로 바꾼다.
- 범용 통과는 회원가입뿐 아니라 이후 모든 BFF 경유 API가 함께 쓴다.

### 2단계 구현 결과

- 범용 Route Handler와 `lib/api/bff/proxyRequest.ts`를 추가했다. 상세 구현과 검증 범위는 [인증 문서](../../architecture/auth.md#범용-통과-구현--검증)를 따른다.
- 새 테스트 47개를 포함한 전체 테스트 353개, ESLint, 변경 파일 Prettier 검사, 타입 검사, 프로덕션 빌드를 통과했다.
- BE의 압축·chunked 요청 지원과 Vercel의 압축·10MB 다운로드 확인은 [결정 대기 항목](../../architecture/auth.md#결정-대기-항목)으로 남긴다.

### 3단계 구현 결과

- 회원가입·온보딩 페이지가 요청별 QueryClient로 약관을 prefetch하고 hydration한다. 공개 약관 요청에만 `next: { revalidate: 3600 }`을 적용한다.
- `getTerms`는 생성 요청 함수와 zod 스키마로 목록을 조회·검증한다. 표시용 구조가 응답 항목과 같아 별도 변환은 하지 않는다.
- 체크 상태는 약관 ID별 객체로 관리한다. 전체 동의는 응답 목록 전체를 대상으로 하고, 전문 동의는 해당 ID만 켠다. 본문은 일반 텍스트로 표시한다.
- 로딩·조회 실패 중에는 두 폼의 제출을 막는다. 실패 시 인라인 재조회 버튼을 표시한다. BE 계약상 빈 목록은 정상 응답이므로 제출할 수 있다.
- 하드코딩 약관과 수신 수단별 체크를 제거했다. API에 요약 필드가 없어 기존 모달 요약도 제거했다.
- 필수 동의·입력값 검증과 회원가입 API 연동은 4단계에서 진행한다.
- 새 테스트 14개를 포함한 전체 테스트 367개, ESLint, 변경 파일 Prettier 검사, 타입 검사, 프로덕션 빌드를 통과했다.

### 4단계 구현 결과

- `isValidEmail`을 로그인·회원가입에서 공유한다. 폼의 필수·길이·비밀번호 확인·업종·필수 약관 검증은 React Hook Form의 `rules`로 처리한다.
- `postSignup`은 생성 요청 함수 `signup`을 호출하고, 요청 구조와 응답을 생성 zod로 검증한다. 업종 값은 생성 타입의 목록을 기준으로 검사한다.
- `industryDetail`은 `CUSTOM`일 때만 보내고, `termsAgreed`는 API 목록 전체의 동의 여부를 전송한다. 선택 약관의 미동의도 `false`로 포함하며, 빈 목록은 빈 배열로 전송한다.
- `formatSignupError`는 가입 실패 5개 코드의 문구를 매핑하고, 폼은 해당 필드에 오류를 표시한다. 그 밖의 오류는 공통 formatter를 거쳐 토스트로 알린다. 실패해도 입력값을 유지하고 재제출할 수 있다.
- 가입 진행 중과 성공 후 이동 전에는 중복 제출을 막고, 성공하면 `/login`으로 이동한다. 가입은 로그인 상태를 만들지 않아 기존 쿼리 캐시를 비우지 않는다.
- 가입 요청 중에는 계정 정보·업종·약관을 잠가 제출값과 서버 오류의 대상이 어긋나지 않게 한다. 잠금 전에 열린 약관 모달에서 뒤늦게 동의 결과가 도착해도 체크 상태를 바꾸지 않는다.
- 필수 약관 오류가 발생하면 목록을 재조회해 새 항목을 표시한다. 이 재조회 중·실패 중에는 제출을 막으며, 재조회 실패는 기존 다시 불러오기 버튼으로 복구한다. mount·창 포커스 같은 백그라운드 갱신 중에는 막지 않는다. 기존 목록으로 제출해도 BE가 필수 약관을 다시 검사한다.
- 업종·약관 컴포넌트에 선택적 오류 표시 props를 추가했다. 온보딩의 기존 제출 동작은 유지한다.
- 새 테스트 59개를 포함한 전체 테스트 426개, ESLint, 변경 파일 Prettier 검사, 타입 검사, 프로덕션 빌드를 통과했다.
