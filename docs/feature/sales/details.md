# 매출 내역 페이지 설계

## 개요

사장님이 월을 선택해 그 달의 매출 합계와 날짜별 기록을 찾고 확인하는 페이지다. 같은 화면에서 매출을 추가·수정·삭제할 수 있지만, 구현은 조회 기능부터 단계적으로 진행한다. 이번 범위에서 "검색"은 **월 변경을 통한 조회**이며 텍스트 검색은 포함하지 않는다.

- Figma: [매출 내역](https://www.figma.com/design/0UAYWaDS9UNjigV73HWcPZ/BizSched?node-id=337-105972&m=dev)
- 라우트: `/sales/details`
- 도메인 공통 사항과 API 명세: [sales/README.md](./README.md)

## 화면 구성

- 페이지 제목과 매출 추가 진입점. 모바일에서는 Figma의 플로팅 액션 버튼을 사용한다.
- 월 선택과 해당 월 합계. 월 선택은 기존 `MonthSelectDropdown`을 사용한다.
- 날짜별 매출 표. **한 행은 하루**이며, 데스크톱·태블릿에는 Figma의 카테고리별 금액과 일 합계를, 모바일에는 날짜와 일 합계를 표시한다.
- 목록 하단 페이지 이동. 기존 `Pagination`을 사용한다.
- 추가 모달, 날짜 행의 인라인 수정, 삭제 확인 흐름. 조회 UI 이후 단계에서 동작을 연결한다.

조회 결과가 없을 때는 빈 상태를, 요청 중에는 로딩 상태를, 실패하면 재시도 가능한 오류 상태를 보여준다. 저장 실패는 현재 입력을 유지하고 오류를 표시한다.

## 상태·데이터

| 상태                                    | 범위        | 도구                             | 근거                                           |
| --------------------------------------- | ----------- | -------------------------------- | ---------------------------------------------- |
| 조회 월                                 | 페이지 URL  | `?month=YYYY-MM`                 | 새로고침·공유·뒤로가기에서 조회 조건 유지      |
| 목록 페이지                             | 페이지 URL  | `?page=` 및 공통 `Pagination` 훅 | 페이지 이동 상태 유지. 1페이지는 파라미터 생략 |
| 월 합계·날짜별 목록                     | 서버 데이터 | TanStack Query                   | 월·페이지 변경 시 조회하고 저장 후 갱신        |
| 추가 모달 열림·편집 중인 날짜·삭제 대상 | 해당 페이지 | 로컬 UI 상태                     | 다른 페이지에서 공유할 필요가 없음             |
| 추가·수정 입력값                        | 각 폼       | React Hook Form                  | 저장 전 입력·검증 상태                         |

- 처음 접속하거나 `month`가 생략되면 한국 시간(`Asia/Seoul`) 기준 이번 달을 조회한다. 날짜·월 경계에도 한국 시간을 사용한다.
- 페이지당 기본 10개를 최신 날짜순으로 표시한다. 마지막 페이지를 초과하면 마지막 페이지로 이동하고 URL을 맞춘다. 1페이지는 `page`를 생략한다.
- 월 변경 시 `page`를 제거해 1페이지로 돌아간다. 조회 키에는 월과 페이지를 포함한다.
- 월 합계는 현재 페이지의 행만 합산한 값이 아니라 **선택한 월 전체**의 값으로 표시한다. 서버 응답과 FE 계산 중 어느 쪽을 단일 출처로 삼을지는 API 명세에서 확정한다.
- 목록 행과 매출 수정·삭제는 하루 단위다. 집계 위치와 API에서 사용하는 기록 식별자는 별도 확정한다.
- 조회 API의 요청·응답 필드는 확정 전이다. 기본 페이지 크기 10개·최신 날짜순·한국 시간 기준은 사용자 확인 사항이다. 목업 UI 단계에서는 FE 표시 타입과 목업 데이터만 두고 DTO를 추정해 만들지 않는다.

### API 연동 계획

1. 확정된 API 명세를 [도메인 문서](./README.md)에 기록한다. API 레이어에서 DTO를 FE 표시 타입으로 변환하고 컴포넌트에는 변환된 데이터만 전달한다.
2. 첫 화면 데이터는 서버에서 요청 단위 QueryClient로 prefetch하고 `HydrationBoundary`를 통해 같은 query options를 쓰는 클라이언트 목록에 전달한다. 월·페이지 변경은 클라이언트에서 조회한다.
3. 추가·수정·삭제는 mutation으로 연결한다. 성공 후 선택 월의 목록과 합계를 갱신하고, 실패 시 폼 입력을 보존한다. 구체적인 오류 코드는 API 명세에 따라 `ts-pattern` 기반 도메인 error formatter에서 처리한다.

## 렌더링 경계

- `page.tsx`는 Server Component로 둔다. 조회 조건을 URL에서 읽고 첫 목록 prefetch를 담당한다.
- 월 선택·페이지 이동·모달·행 편집·mutation을 사용하는 가장 말단 영역에만 `"use client"`를 둔다.
- Server → Client로 넘기는 FE 데이터는 문자열·숫자·배열·일반 객체만 사용한다. `Date` 객체와 서버 전용 모듈을 넘기지 않는다.
- 서버 fetcher는 쿠키 인증을 명시적으로 전달하고 사용자별 응답을 캐시하지 않는다. 서버/클라이언트 fetcher 구조는 [데이터 흐름 문서의 미확정 사항](../../architecture/data-flow.md#결정-대기-항목)을 확정한 뒤 선택한다.

[렌더링 금지 목록](../../architecture/rendering.md#금지-목록-리뷰-체크리스트)은 구현 PR에서 항목별로 점검한다.

## 설계 결정

| 결정                                       | 근거                                                                                                                                                                                                         |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/sales/details`를 매출 내역 라우트로 사용 | [폴더 구조 문서](../../architecture/folder-structure.md)의 `sales/details` 구조와 일치한다. 현재 `ROUTE_PATHS.sales()`와 대시보드의 `/sales` 링크는 기존 코드와 차이가 있으므로 페이지 연결 PR에서 수정한다. |
| 조회 조건은 월 하나                        | 첫 구현의 목적이 기간별 내역 조회다. Figma의 월 선택 UI와 맞고 별도 검색 입력이 필요 없다.                                                                                                                   |
| 월·페이지를 URL로 관리                     | 결과 링크 공유와 뒤로가기를 지원한다. 월 변경 시 이전 월의 페이지 번호가 남지 않도록 1페이지로 초기화한다.                                                                                                   |
| 날짜 단위 행                               | Figma의 날짜별 카테고리 금액·일 합계 표와 사용자 확인을 따른다.                                                                                                                                              |
| 조회 기능을 먼저 구현                      | API 명세가 확정되기 전에 저장 계약을 추정하지 않는다. 전체 추가·수정·삭제 흐름은 문서에 유지한다.                                                                                                            |
| 기존 공통 UI 재사용                        | 월 선택·페이지 이동·플로팅 액션을 위한 별도 공통 추상화를 만들지 않는다.                                                                                                                                     |

## 단계별 PR 계획

| 순서 | 브랜치                         | base                      | 범위                                                                   | 완료 기준                                           |
| ---- | ------------------------------ | ------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------- |
| 1    | `feat/sales-details-docs`      | `dev`                     | 도메인·페이지 설계와 문서 인덱스                                       | 조회 범위와 후속 기능 경계가 명시됨                 |
| 2    | `feat/sales-details-ui`        | `feat/sales-details-docs` | 월 선택, 합계, 날짜별 표, 페이지 이동, 반응형·빈 상태                  | Figma의 데스크톱·태블릿·모바일 구성과 URL 상태 확인 |
| 3    | `feat/sales-details-form-ui`   | `feat/sales-details-ui`   | 추가 모달, 행 인라인 수정, 삭제 확인                                   | 키보드 조작과 입력 검증 확인                        |
| 4    | `feat/sales-details-read-api`  | `dev`                     | 명세 확정, DTO 변환, 월·페이지 조회, 첫 화면 hydration, 로딩·오류 상태 | 월 이동·페이지 이동·재시도와 월 전체 합계 확인      |
| 5    | `feat/sales-details-write-api` | `dev`                     | 추가·수정·삭제 mutation, 오류 메시지, 목록·합계 갱신                   | 성공·실패 시 데이터와 입력 상태 확인                |

1→2→3은 UI 작업을 stacked PR로 쌓는다. 1이 병합되면 2의 base를 `dev`로, 2가 병합되면 3의 base를 `dev`로 바꾸고 각각 최신 `dev`에 맞춰 브랜치 이력을 정리한다.

UI PR 세 개가 모두 `dev`에 병합된 뒤 4를 최신 `dev`에서 분기·병합한다. 5는 4가 병합된 뒤 최신 `dev`에서 분기한다. 따라서 API PR 두 개의 base는 `dev`이며, 동시에 열어 두는 stacked PR은 아니다.

## 확인 필요

아래 항목은 구현 중 임의로 확정하지 않고 해당 단계 전에 확인해 [도메인 문서](./README.md)에 기록한다.

- 조회·추가·수정·삭제 API 계약과 카테고리 식별 방식
- 월 합계와 날짜별 합계를 서버에서 계산해 받을지, 프론트에서 계산할지 백엔드와 확인한다. 하루 단위 수정·삭제 API의 기록 식별자도 함께 확인한다.
- 저장 오류 코드와 사용자 메시지, 삭제 확인 문구
