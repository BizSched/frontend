# 매출 대시보드 페이지 설계

## 개요

사용자가 매출 요약, 추이, 카테고리 구성, 최근 입력 내역을 확인하고 매출을 관리하는 페이지다. 라우트는 사용자가 지정한 `/sales`이며, `ROUTE_PATHS.sales()`와 일치한다. [Figma 매출 대시보드 섹션](https://www.figma.com/design/0UAYWaDS9UNjigV73HWcPZ/BizSched?node-id=337-105747)의 데이터가 표시된 데스크톱 화면(`337:105748`)과 모바일 화면(`337:105893`), 빈 상태(`337:105786`)를 최종 시각 기준으로 삼는다.

이 문서는 매출 대시보드의 **전체 완성 범위**를 다룬다. 정적 UI, 빈 상태, 기간·차트 단위 필터, 매출 조회, 입력·수정·삭제, 상세 내역 이동을 단계적으로 연결한다. **첫 UI PR은 데이터가 표시된 데스크톱·모바일 정적 UI를 범위로 한다.** 이후 동작의 계약이 확정되지 않은 부분은 `확인 필요`에 남긴다.

## 화면 구성

| 영역               | 표시 내용                                                | 구성 책임                                                                           |
| ------------------ | -------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 공통 레이아웃      | Sidebar, 모바일 상단 바                                  | 기존 `app/(main)/layout.tsx`와 `AppSidebar` 재사용                                  |
| 페이지 헤더        | `매출 대시보드`, `오늘 매출 입력` 액션                   | 페이지 제목과 진입 액션의 배치                                                      |
| 요약 카드          | 이번 달 누적, 전월 대비 증감, 전년 대비                  | 공통 `Card` 위에 도메인별 내용 조합                                                 |
| 매출 차트 카드     | 제목, 월 선택 표시, 주·월·연 탭 표시, 누적 막대와 범례   | 카드 외곽은 도메인, 플롯은 [Chart 설계](../../component/chart/README.md) 기준       |
| 카테고리 구성 카드 | 기간 표기, 도넛, 범례                                    | 카드 외곽은 도메인, 도넛은 Chart 설계 기준                                          |
| 입력한 매출 카드   | 날짜와 카테고리별 금액, 합계, 최근 8일 요약, 더보기 표시 | 데스크톱 표는 `dev`의 공통 `Table`을 사용하고, 모바일 표시는 Figma 구성에 맞춰 조합 |
| 빈 상태            | 매출 기록이 없을 때의 요약·차트·내역 표시                | Figma 빈 화면 기준으로 후속 단계에서 연결                                           |
| 입력·수정 흐름     | 오늘 매출 입력, 내역 수정·삭제                           | 별도 폼과 동작 계약 확정 후 연결                                                    |

두 화면의 배치와 반응형 전환은 Figma 인스턴스를 기준으로 검수한다. 모바일 헤더·내비게이션은 기존 공통 레이아웃을 따르고, 스타일은 [desktop-first 규칙](../../convention/style.md)과 기존 색상·타이포그래피 토큰을 따른다.

## 상태·데이터

| 상태·데이터        | 최종 책임                        | 정적 UI PR       | 후속 단계                                                                                        |
| ------------------ | -------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------ |
| 요약 금액·비율     | 매출 집계 서버 상태              | 목업 값          | 조회 API와 TanStack Query 연결                                                                   |
| 차트와 카테고리 값 | 기간별 매출 서버 상태            | 목업 값          | 조회 API와 TanStack Query 연결                                                                   |
| 최근 입력 내역     | 매출 내역 서버 상태              | 목업 행          | 조회 API와 TanStack Query 연결                                                                   |
| 선택 월·차트 단위  | 필터 상태                        | 대표 상태로 고정 | 기간 선택과 주·월·연 전환 연결. URL 공유 필요 여부 확인 후 URL Search Params 또는 로컬 상태 선택 |
| 입력·수정·삭제     | 폼 및 mutation 상태              | 미구현           | React Hook Form과 TanStack Query mutation, 성공 후 관련 query 무효화                             |
| 빈 상태            | 조회 결과에서 파생되는 표시 상태 | 미구현           | 데이터 유무에 따라 Figma 빈 상태 표시                                                            |

목업 데이터는 실제 서버 값으로 오해하지 않도록 도메인 화면 전용으로 관리한다. 표시 숫자와 날짜는 Figma 대표 상태를 재현하기 위한 값이며, 비즈니스 규칙이나 API 계약으로 취급하지 않는다.

최종 데이터 흐름은 [데이터 흐름 규칙](../../architecture/data-flow.md)의 `API DTO → Formatter → FE DAO → TanStack Query → UI`를 따른다. 필요한 데이터는 집계 금액과 비교 수치, 기간별·카테고리별 금액, 날짜별 입력 내역 및 합계다. 엔드포인트·DTO 필드·검증 규칙은 백엔드 명세를 받은 뒤 도메인 문서에 확정한다. 오류 코드는 도메인 formatter와 `ts-pattern`으로 표시 메시지에 매핑한다.

## 렌더링 경계

`app/(main)/sales/page.tsx`는 Server Component로 둔다. 정적 카드와 목록도 Server Component를 기본으로 한다. 정적 UI PR에서 차트 라이브러리 또는 공통 UI가 클라이언트 런타임을 요구하는 경우에만 해당 말단 컴포넌트에 클라이언트 경계를 둔다. 페이지나 레이아웃 전체에 `"use client"`를 추가하지 않는다.

API 연결 단계에서는 첫 화면에 필요한 매출 데이터를 [렌더링 규칙](../../architecture/rendering.md)에 따라 서버에서 prefetch하고, 동일한 query options를 `HydrationBoundary` 안의 클라이언트 조회에 재사용한다. 인증된 매출 데이터는 요청 간 캐시하지 않는다. 필터·입력·수정·삭제의 이벤트 경계는 필요한 말단 컴포넌트에 둔다.

## 설계 결정

- 라우트는 사용자 결정에 따라 `/sales`로 확정한다. [폴더 구조 문서](../../architecture/folder-structure.md)의 계획 예시에는 `app/sales/dashboard/`가 있으나 실제 `ROUTE_PATHS.sales()`는 `/sales`다. 이번 페이지는 현재 코드의 경로를 따른다.
- 기존 Sidebar·Card를 재사용하고 매출 의미를 가진 카드 조합은 `src/components/sales/`에 둔다. 공통 컴포넌트에 매출 데이터를 넣지 않는다.
- 공통 `Table`과 `Chart`는 `dev`에 구현되어 있다. 정적 UI 브랜치는 문서 브랜치에서 분기해 PR을 쌓고 공통 컴포넌트를 재사용한다. 문서 PR이 `dev`에 병합되면 UI PR의 base를 `dev`로 변경한다.
- 차트 인스턴스의 시각적 오류보다 [Chart 설계 문서의 원본 컴포넌트 기준](../../component/chart/README.md#화면-인스턴스와-컴포넌트가-다를-때)을 우선한다.
- 빈 화면(`337:105786`)과 편집 중 행은 최종 범위에 포함한다. 정적 UI PR에서는 데이터가 표시된 대표 화면만 구현한다.

## 단계별 PR 계획

| 순서           | 브랜치                      | base                                                | 범위                                                                                   | 완료 기준                                                                                              |
| -------------- | --------------------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 1. 문서        | `feat/sales-dashboard-docs` | `dev`                                               | 매출 도메인·대시보드 페이지 설계와 문서 인덱스 정리                                    | PR 변경 파일이 문서 4개로 한정되고, 정적 UI와 후속 기능의 범위·미확정 사항·문서 링크가 일치한다.       |
| 2. 정적 UI     | `feat/sales-dashboard-ui`   | `feat/sales-dashboard-docs` (문서 PR 병합 후 `dev`) | `/sales`의 데이터가 표시된 데스크톱·모바일 화면, 화면용 데이터, 필요한 내비게이션 연결 | 공통 Table·Chart를 재사용하고, 데스크톱·모바일 화면 검수와 관련 테스트·타입 검사·린트·빌드를 통과한다. |
| 3. 후속 UI     | 확인 필요                   | 정적 UI PR 병합 후 최신 `dev`                       | 빈 상태, 기간·차트 단위 필터, 더보기 이동, 입력·수정·삭제 폼과 화면 전환               | 동작 계약을 확정한 뒤 화면과 상호작용을 검증한다.                                                      |
| 4. 데이터 연동 | 확인 필요                   | 후속 UI PR 병합 후 최신 `dev`                       | 백엔드 계약에 따른 집계·차트·내역 조회와 입력·수정·삭제 mutation                       | API 계약을 반영하고 조회·변경·로딩·오류 상태를 검증한다.                                               |

## 확인 필요

- [스타일 규칙의 미확정 항목](../../convention/style.md#breakpoint): 1920px `desktop` 경계를 실제 노트북 폭에도 그대로 적용할지. 정적 UI PR에서는 기존 토큰을 변경하지 않는다.
- 실제 API 엔드포인트, DTO, 매출 입력·수정·삭제의 검증 및 오류 코드는 후속 작업에서 확정한다.
- 필터를 URL에 보존할지, 입력·수정 UI가 모달인지 별도 페이지인지, `더보기`의 목적지는 후속 동작 설계에서 확인한다.
