# 매출 기능 문서

## 개요

사장님이 매출 현황을 요약해서 확인하고 월별·날짜별 기록을 관리하는 도메인이다. 매출 대시보드는 요약·추이·카테고리 구성을, 매출 내역은 월별 목록 조회와 추가·수정·삭제를 담당한다. API 연동 전에는 목업 데이터로 UI와 인터랙션을 구현한다.

## 주요 화면 / 플로우

| 화면          | 라우트             | 문서                           | 정적 UI PR                                               |
| ------------- | ------------------ | ------------------------------ | -------------------------------------------------------- |
| 매출 대시보드 | `/sales/dashboard` | [dashboard.md](./dashboard.md) | 데이터가 표시된 대표 화면의 데스크톱·모바일 정적 UI      |
| 매출 내역     | `/sales/details`   | [details.md](./details.md)     | 월 선택, 월 합계와 날짜별 내역 조회, 매출 추가·수정·삭제 |

- `/sales` 접속은 `/sales/dashboard`로 리다이렉트한다. `next.config.ts`에서 307 리다이렉트로 처리한다.
- 대시보드는 정적 UI PR 검토 단계다. 화면 구성과 후속 범위는 [대시보드 페이지 설계](./dashboard.md)를 따른다.
- 매출 내역은 **조회 UI → 추가·수정·삭제 인터랙션 → API 연동** 순서로 진행한다. 조회 조건은 월 하나이며 자유 텍스트 검색이나 카테고리 필터는 이번 범위에 없다.
- 대시보드의 모두 보기 목적지는 `/sales/details`로 확정했다(2026-10-05, #152). 입력 폼 공유 방식은 대시보드 후속 동작 설계에서 확정한다.

## API 명세

백엔드 Swagger(`orval` 코드젠, `src/lib/api/generated/`)에 명세가 확정되어 있다. 아래는 매출 내역(`/sales/details`) 조회에 쓰는 엔드포인트다. 예시 화면의 숫자와 카테고리명으로 DTO를 임의로 확정하지 않고 이 스펙을 따른다.

| 용도             | 엔드포인트                                       | 비고                                                                                                                       |
| ---------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 날짜별 목록 조회 | `GET /api/sales?month=&page=&size=` (`findAll3`) | 날짜 내림차순. `month` 생략 시 전체 기간. 날짜별 합계는 `SaleResponse.totalAmount`                                         |
| 월 전체 합계     | `GET /api/sales/summary?month=` (`findSummary`)  | 원래 대시보드 상단 카드용. 응답의 `totalAmount`만 추려 쓰고 `previousMonth`·`previousYear`는 무시 (사용자 확인 2026-10-10) |
| 매출 등록        | `POST /api/sales` (`create3`)                    | 같은 날짜 중복 등록 시 409 (write-api 범위)                                                                                |
| 매출 수정        | `PUT /api/sales/{salesId}` (`update`)            | 부분 수정 아님, 통째로 교체 (write-api 범위)                                                                               |
| 매출 삭제        | `DELETE /api/sales/{salesId}` (`_delete`)        | 하루 전체 삭제, 204 (write-api 범위)                                                                                       |

- 기록 식별자는 `SaleResponse.id`(`salesId`)이며 하루 단위다.
- 카테고리는 이름이 아니라 `categoryId`로 식별한다. 이름 변경과 무관하게 동일 카테고리를 가리킨다.
- 금액은 0 이상 정수, 생략 시 0. 날짜는 미래 불가.

### 매출 내역 쓰기 API

기준: `src/lib/api/generated/sales/sales.ts`, `src/lib/api/generated/sales/sales.zod.ts`

| 작업 | 요청                                             | 성공 응답        | 계약                                                                                                                                                                                                                                                 |
| ---- | ------------------------------------------------ | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 추가 | `POST /api/sales` — `SaleCreateRequest`          | `SaleResponse`   | 하루 한 건. 날짜는 `yyyy-MM-dd`, 미래 날짜는 불가. 카테고리별 금액은 원 단위 0 이상의 정수이며, `totalAmount`는 금액 합계와 같아야 한다. 미포함 카테고리는 0원으로 저장된다. 이미 매출이 있는 날짜는 409이며 수정 API를 사용한다.                    |
| 수정 | `PUT /api/sales/{salesId}` — `SaleUpdateRequest` | `SaleResponse`   | `salesId`는 날짜별 매출 ID다. 요청에 날짜가 없으므로 날짜는 수정할 수 없다. 보낸 카테고리 금액 전체로 교체되며 빠진 카테고리는 0원이 된다. 기존 값을 보존하려면 수정 시 현재 카테고리 전체 금액을 전송한다. `totalAmount`는 금액 합계와 같아야 한다. |
| 삭제 | `DELETE /api/sales/{salesId}`                    | `204 No Content` | 매출 ID에 해당하는 날짜의 매출 전체와 카테고리별 금액을 삭제한다.                                                                                                                                                                                    |

추가·수정의 응답은 `SaleResponse`이며 `id`, `date`, `sales`(카테고리 ID·이름·금액), `totalAmount`를 포함한다. 생성 계약에 명시된 HTTP 오류는 같은 날짜 중복의 409다. 현재 생성된 계약에는 매출 전용 `errorCode` 목록이나 다른 오류별 메시지가 정의되어 있지 않으므로, 도메인 코드를 추정하거나 formatter에 임의 매핑하지 않고 공통 오류 처리로 표시한다. 백엔드가 매출 전용 코드를 제공하면 이 문서와 formatter를 함께 갱신한다.

조회 UI는 아래 확정된 조회 규칙을 따른다. 매출 삭제 확인 문구는 “해당 날짜의 매출 전체를 삭제할까요? 삭제한 내역은 복구할 수 없습니다.”로 확정했다.

## 카테고리 관리

- 사용자 확인(2026-10-03): 카테고리는 사용자가 추가하고 이름을 변경할 수 있다. 화면의 카테고리명은 고정 목록이나 식별 코드로 취급하지 않는다.
- [Figma 카테고리 관리·폼 상태](https://www.figma.com/design/0UAYWaDS9UNjigV73HWcPZ/BizSched?node-id=337-106366)에서 기존 이름 입력, 신규 이름 입력과 추가 버튼, 행별 삭제, 저장·되돌리기 버튼을 확인했다.
- 중복 생성 상태는 `중복된 이름입니다.` 오류와 비활성 추가 버튼을 표시한다. 이름의 앞뒤 공백을 제거하고 빈 이름을 허용하지 않는다. 이름은 공백 제거 후 1~10자이며, 중복 비교도 공백을 제거한 값으로 한다(API 계약). 영문 대소문자 구분은 미정이다.
- 삭제 확인 팝업은 `정말 삭제하시겠어요?`, `삭제된 카테고리는 복구할 수 없습니다.` 문구와 취소·삭제 버튼을 사용한다. 이는 카테고리 삭제 디자인이며 매출 기록 삭제 문구로 일반화하지 않는다.
- 이름 변경과 무관하게 같은 카테고리를 식별할 수 있어야 한다. API 식별자 필드명·자료형·발급 방식은 백엔드 계약에서 확정한다. 기존 목업의 `product`, `service` 등 고정 키를 실제 API 계약으로 확정하지 않는다.
- 사용자 확인(2026-10-14): 추가와 삭제는 즉시 서버에 반영하고, 이름 변경만 관리 폼의 임시 값으로 두었다가 저장 버튼으로 확정한다.
  - 추가: 추가 버튼을 누르면 `POST /api/sales/categories`로 바로 만든다. `color`·`order`는 서버가 배정한다.
  - 삭제: 삭제 확인 팝업에서 삭제를 선택하면 `DELETE /api/sales/categories/{categoryId}`로 바로 지운다. 팝업의 "복구할 수 없습니다" 문구와 일치한다.
  - 이름 변경: 저장 버튼을 누르면 `PUT /api/sales/categories`로 전체 목록의 `id`·`name`·`order`를 보낸다. 이 요청은 원자적이다. 이름 중복은 저장 전에 폼에서 공백을 제거한 이름끼리 비교해 해당 입력칸에 표시한다. `ApiError`가 응답 `data`를 보관하지 않아 409 `CATEGORY_NAME_DUPLICATED`의 `duplicatedIds`는 쓰지 않고, 동시 수정으로 생긴 409는 일반 오류 문구로 표시한다.
  - 이전 결정(2026-10-03, 추가·이름 변경·삭제를 모두 저장 시 확정)은 API 계약 전 Figma의 저장·되돌리기 버튼을 근거로 정했다. 계약상 원자적 일괄 API는 이름·순서 변경뿐이라 저장 한 번이 여러 요청으로 나뉘고 부분 실패가 생기며, 새 카테고리의 서버 배정 색을 저장 전에 표시할 수 없어 변경했다.
- 저장하지 않고 관리 화면을 나갔다가 다시 열면 임시 이름 변경을 버리고 서버의 현재 값을 표시한다.
- 사용자 확인(2026-10-14, 변경): 관리 화면을 "새 카테고리"(추가 즉시 반영)와 "이름 수정"(저장·되돌리기 대상) 섹션으로 나눈다. 저장 버튼 하나가 담당하는 입력만 한 영역에 묶어, 화면이 약속하는 저장 범위를 API의 원자적 범위(`PUT`)와 맞춘다.
  - 추가·삭제를 임시 상태로 두고 저장 시 `DELETE`→`POST`→`PUT`으로 보내는 안은 기각했다. 중간 실패 시 되돌릴 수 없는 반쪽 상태가 남는다(삭제 복구 API 없음, 재생성 시 새 `id`·`color`).
- 사용자 확인(2026-10-14, 변경): 저장하지 않은 이름 변경이 있는 상태에서 추가·삭제가 성공해도 이름 변경을 `categoryId` 기준으로 유지한다. 이전 결정(추가·삭제 시 버림)은 섹션 분리 후 "추가가 수정 중인 이름을 지운다"는 동작이 두 영역이 독립이라는 화면 신호와 어긋나 변경했다.
- 사용자 제공 기능 명세: 카테고리 이름은 중복될 수 없고 최대 10개까지 생성한다.
- 되돌리기는 폼을 닫지 않고 저장하지 않은 이름 변경을 서버의 현재 값으로 복원한다. 이미 반영된 추가·삭제는 되돌리지 않는다. 섹션 분리로 되돌리기가 "이름 수정" 영역에만 해당함을 화면에서 드러낸다.
- 이름 변경을 저장하면 과거 내역에도 새 이름으로 통일한다. 카테고리를 삭제해도 과거 매출 금액과 합계는 유지한다. 삭제된 카테고리는 매출 목록(`GET /api/sales`)의 `sales`에서 빠지고 차트·비중에는 남는다(API 계약).
- 확인 필요: 영문 대소문자 구분. 삭제된 카테고리가 있는 날짜를 수정할 때 매출 수정(`PUT /api/sales/{salesId}`, 전체 교체·`totalAmount` 합계 일치)이 지운 카테고리의 과거 금액을 어떻게 처리하는지 백엔드에 확인한다.

## 매출 조회·입력 규칙

사용자 제공 기능 명세와 사용자 확인(2026-10-03)을 기준으로 한다.

- 내역 페이지의 기본 페이지 크기는 10개다. 월 전체 합계는 현재 페이지의 합계와 구분한다.
- 그래프는 연·월·주 단위로 조회한다. 주간 범위는 **월요일~일요일**이다. 기능 명세 이미지의 일요일~토요일 예시보다 이후 사용자 결정을 우선한다.
- 카테고리 구성의 금액·비중은 **당월 매출** 기준이다. 당일 매출 기준으로 해석하지 않는다. 월 선택과의 연동은 후속 동작 설계에서 확인한다.
- 매출 추가는 날짜와 카테고리별 금액을 입력하는 하루 단위다. 이미 매출이 있는 날짜를 다시 추가하려 하면 기존 내역 수정을 안내한다. 더하거나 덮어쓰지 않는다.
- 미입력 금액은 0원으로 처리하며 0원 입력을 허용한다. API 계약상 금액은 0 이상의 원 단위 정수이고 미래 날짜는 허용하지 않는다. 최대 금액은 명세에 없다.
- 매출 수정은 하루의 카테고리별 수정 내용을 한 번에 전송하고, 매출 삭제는 하루 전체를 대상으로 한다. 쓰기 API 식별자와 요청 형식은 [매출 내역 쓰기 API](#매출-내역-쓰기-api)를 따른다.
- 사용자 확인(2026-10-03): 처음 접속하거나 `month` 파라미터가 없으면 한국 시간(`Asia/Seoul`) 기준 이번 달을 조회한다. 날짜와 월 경계도 한국 시간을 기준으로 한다.
- 날짜별 내역은 최신 날짜순으로 정렬한다. 마지막 페이지보다 큰 페이지 번호로 접근하면 마지막 페이지로 이동하고 URL도 해당 페이지로 맞춘다. 1페이지 URL은 기존 규칙대로 `page`를 생략한다.

## 상태 관리 포인트

- 대시보드의 정적 UI는 표시용 목업 데이터를 사용한다. 기간·차트 단위 필터의 URL 보존 여부는 후속 동작 설계에서 결정한다.
- 매출 내역의 조회 월과 페이지는 URL 검색 파라미터로 관리한다. 월 변경 시 페이지를 1로 초기화한다. 1페이지 URL 표기는 [Pagination 설계](../../component/pagination/README.md)의 규칙을 따른다.
- API 연동 후 매출 집계·목록·월 합계는 TanStack Query로 관리하고, 추가·수정·삭제 성공 후 관련 데이터를 갱신한다.
- 모달 열림과 행 편집 상태는 페이지 내부 상태로 둔다. 입력 폼 상태는 React Hook Form을 사용한다. API 연결 전 목업 변경의 보존 범위는 인터랙션 구현 전에 확인한다.

## 주요 컴포넌트

- 대시보드는 기존 Sidebar·Card·Chart·Table을 재사용하고 요약·차트·최근 내역을 매출 도메인 컴포넌트로 조합한다.
- 매출 내역의 월 선택은 [MonthSelectDropdown](../../component/month-select-dropdown/README.md), 날짜별 표는 [Table](../../component/table/README.md), 페이지 이동은 [Pagination](../../component/pagination/README.md)을 사용한다.
- 추가 진입점은 화면 크기에 따라 [Button](../../component/button/README.md) 또는 [ActionButton](../../component/ActionButton/README.md)을 활용한다. 날짜별 행과 입력 폼은 매출 도메인 컴포넌트로 둔다.
- 공통 컴포넌트에는 매출 API나 집계 규칙을 넣지 않는다.

매출 데이터는 [데이터 흐름 규칙](../../architecture/data-flow.md)에 따라 DTO를 FE 표시 타입으로 변환하고 오류를 처리한다. 공통 Table과 Chart의 기본 UI는 dev에 병합되어 있으며, 차트 조합은 [Chart 설계](../../component/chart/README.md)를 따른다.
