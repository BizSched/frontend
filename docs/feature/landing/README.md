# 랜딩 페이지 설계

## 개요

처음 방문한 사용자에게 BizSched의 핵심 기능을 소개하고 로그인으로 진입시키는 정적 페이지다. 라우트는 루트 `/`이며 `app/page.tsx`가 진입점이다. [Figma 랜딩페이지 섹션](https://www.figma.com/design/0UAYWaDS9UNjigV73HWcPZ/BizSched?node-id=324-99750)의 태블릿(744px)·모바일(375px) 프레임을 시각 기준으로 삼는다.

랜딩은 페이지가 하나뿐이고 API·상태가 없으므로 도메인 문서와 페이지 문서를 나누지 않고 이 문서 하나로 관리한다.

## 상태·데이터

상태와 API가 없는 정적 페이지다. 문구·이미지는 컴포넌트에 직접 둔다.

## 렌더링 경계

`app/page.tsx`와 모든 섹션을 Server Component로 둔다. CTA는 `next/link`로 이동하므로 클라이언트 경계가 필요 없다.

## 설계 결정

- **라우트는 `app/page.tsx`(`/`)에 둔다.** Next.js App Router에서 루트 URL의 진입점은 `app/page.tsx`이고, [폴더 구조 문서](../../architecture/folder-structure.md#app-구조)도 같은 위치를 정의한다. Route Group(`app/(landing)/page.tsx`)은 랜딩 전용 layout이 필요할 때만 의미가 있다. 현재 랜딩은 루트 layout 외에 공유할 layout이 없고, Sidebar layout은 이미 `app/(main)/`로 분리되어 있으므로 그룹을 추가하지 않는다. 같은 `/`를 가리키는 `app/page.tsx`와 그룹 page는 공존할 수 없다.
- **CTA 목적지는 `/login`이다.** 회원가입은 한 번이고 로그인은 반복되므로 다수 방문 흐름인 로그인을 입구로 둔다. 신규 사용자는 로그인 화면의 `회원가입` 링크로 이동한다.
- **CTA는 `Link`에 공통 `buttonVariants`를 적용한다.** 동작이 페이지 이동이므로 `<button>`이 아니라 `<a>`가 맞다. 공통 `Button`은 `<button>`을 렌더링하므로 스타일만 `buttonVariants`로 재사용한다. 태블릿 이상은 `large`, 모바일은 `small` 크기를 쓰고 Figma의 주황 그림자만 className으로 더한다.
- **744px보다 넓은 화면은 태블릿 레이아웃을 가운데 정렬한다.** Figma에 PC 프레임이 없다. [desktop-first 규칙](../../convention/style.md#반응형--desktop-first)에 따라 태블릿 디자인을 기본 클래스로, 모바일을 `max-tablet:`으로 작성한다. 배경은 전체 폭, 콘텐츠는 744px 폭으로 가운데에 둔다.
- **복합 일러스트는 Figma에서 이미지로 export해 쓴다.** 알림 말풍선·특징 섹션 장식은 회전·마스크가 겹친 수십 개 레이어라 마크업으로 재현하면 유지보수 비용만 늘어난다. 파일은 `src/assets/images/landing/`에 두고 `next/image`로 렌더링한다. 장식 이미지는 `alt=""`, 서비스 화면 이미지는 화면 내용을 설명하는 대체 텍스트를 둔다.
- **제목 구조**: 히어로의 큰 문구를 `h1`, 각 섹션의 큰 문구를 `h2`, 시작 단계 카드 제목을 `h3`으로 둔다. 큰 문구 위의 작은 문구는 `p`로 둔다.

## 확인 필요

- **헤더 유무**: Figma에 헤더가 없는 것은 디자인 의도가 아니다. 헤더(로그인 링크)가 추가되면 CTA를 `/signup`으로 바꿀지 다시 판단한다.
- **PC 시안**: 시안이 생기면 기본 클래스를 PC 레이아웃으로 바꾸고 태블릿을 `max-desktop:`로 내린다.
- **로그인 사용자의 `/` 접근**: 인증 구현 후 대시보드로 보낼지 결정한다.
