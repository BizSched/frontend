# Code Review Checklist — 일반 기준

이 파일은 **프로젝트 문서에 없는 일반 점검**만 다룬다.
네이밍, 레이어 책임, 렌더링 경계, 상태 도구 선택, 환경변수, 스타일, 커밋 규칙의 단일 출처는
`docs/architecture/*` · `docs/convention/*`이며, 요약은 `docs/collaboration/code-review.md`다.
**여기에 프로젝트 규칙을 다시 쓰지 않는다.** 프로젝트 규칙 점검은 SKILL.md Step 6 표를 따른다.

변경과 무관한 섹션은 건너뛴다. 각 항목은 **실제 영향을 설명할 수 있을 때만** finding이 된다.

---

## Correctness

- [ ] async 작업이 await되고, Promise rejection이 처리되거나 위로 전파되는가
- [ ] 동시 상태 갱신에 경쟁 조건이 없는가 (stale closure, 배칭)
- [ ] 조건 분기가 빠짐없이 처리되는가 — 조용히 아무것도 하지 않는 경로가 없는가
- [ ] 의도한 곳에서만 데이터가 변경되는가 (의도치 않은 참조 공유 없음)
- [ ] 호출부가 반응해야 하는 반환값을 확인하는가
- [ ] 이 변경이 기존 호출부의 동작을 바꾸지 않는가 (회귀)

> 요구사항 적합성·엣지 케이스는 `docs/collaboration/code-review.md`의 "사람이 확인할 사항" 참고.

---

## Security

**문서 규칙과 충돌하더라도 보안·사용자 데이터 노출 위험은 항상 보고한다.**

- [ ] 사용자 입력이 HTML·파일 경로·셸 명령·쿼리에 들어가기 전에 검증·이스케이프되는가
- [ ] `dangerouslySetInnerHTML` / `innerHTML` 값의 출처가 신뢰 가능한가
- [ ] `eval()` / `new Function()` 이 없는가
- [ ] 리다이렉트 대상이 검증되는가 (open redirect)
- [ ] 인증·인가가 데이터를 반환하기 **전에** 확인되는가
- [ ] 인증·사용자별 응답이 요청 간 공유되는 캐시에 들어가지 않는가
- [ ] 새로 추가된 의존성이 널리 쓰이고 관리되는 패키지인가
- [ ] `Dockerfile` / GitHub Actions에 값이 직접 들어있지 않고 secrets로 참조되는가
- [ ] GitHub Actions에서 `${{ github.event.* }}` 를 `run:` 안에 직접 보간하지 않는가 (스크립트 인젝션)

> 환경변수 노출(`NEXT_PUBLIC_`, server 전용 값)의 단일 출처는 `docs/architecture/env.md`.

---

## Performance

**실제 렌더링·번들·네트워크 비용이 확인될 때만 보고한다.**
"최적화할 수 있다"는 이유만으로는 finding이 아니다. 무엇이 얼마나 비싼지 말할 수 있어야 한다.

- [ ] 렌더 경로나 요청 핸들러 안에서 반복 호출(N+1)이 발생하는가
- [ ] 서로 독립적인 요청이 순차 실행되어 워터폴이 되는가
- [ ] 큰 데이터셋을 페이지네이션·스트리밍 없이 한 번에 메모리에 올리는가
- [ ] 요청 경로에 동기 블로킹 호출이 있는가
- [ ] 매 렌더마다 새로 만들어지는 값이 실제로 하위 트리 재렌더를 유발하는가

> 메모이제이션·`next/image`·`next/dynamic`의 **미사용 자체는 지적하지 않는다.** SKILL.md "강제하지 않을 것" 참고.

---

## TypeScript

- [ ] `as` 캐스팅에 근거가 있는가 (에러를 덮으려고 쓰지 않았는가)
- [ ] non-null assertion(`!`)의 가정이 실제로 보장되는가
- [ ] 외부에서 오는 알 수 없는 데이터를 `any` 대신 `unknown`으로 받고 좁히는가
- [ ] 공개 API 경계(다른 레이어에서 쓰는 함수·타입)의 시그니처가 추론에만 의존해 모호하지 않은가

> 반환 타입 명시를 일괄 요구하지 않는다. 추론 결과가 모호하거나 잘못 추론될 때만 지적한다.
> `interface` 사용, `as const` 등 타입 컨벤션은 `docs/convention/` 문서가 단일 출처.

---

## React

- [ ] `useEffect` 의존성 배열이 실제 사용 값과 일치하는가 (stale closure)
- [ ] 구독·타이머·이벤트 리스너에 cleanup이 있는가
- [ ] 리스트 `key`가 안정적인 고유 ID인가 (배열 인덱스 아님)
- [ ] `useEffect` 콜백이 async 함수 자체가 아닌가
- [ ] 조건부 렌더링에서 `0`·빈 문자열이 의도치 않게 렌더되지 않는가

---

## TanStack Query  *(관련 변경이 있을 때만)*

- [ ] query key가 도메인별 factory(`xxxKeys`)로 정의되고 `as const`가 붙었는가
- [ ] 캐시를 구분해야 하는 최소 파라미터가 key에 포함됐는가
- [ ] 서버와 클라이언트가 **같은 `xxxQueryOptions`** 를 공유하는가 (queryKey/queryFn 중복 정의 없음)
- [ ] mutation 성공 후 영향받는 query의 invalidation(또는 `setQueryData`)이 있는가
- [ ] 첫 화면 데이터가 prefetch → `dehydrate` → `HydrationBoundary` → `useQuery` 흐름을 따르는가
- [ ] prefetch 대상이 첫 화면·SEO 데이터로 한정됐는가 (모달·탭 뒤·무한 스크롤 다음 페이지 제외)

> 상세 규칙: `docs/architecture/state-management.md`, `docs/architecture/rendering.md`.

---

## React Hook Form  *(관련 변경이 있을 때만)*

- [ ] 폼 값을 RHF가 관리하면서 같은 값을 `useState`로 **이중 관리**하지 않는가
- [ ] 필드 정의·유효성 검사·초기값이 흩어지지 않고 한 곳에 모여 있는가
- [ ] 제출 중 상태를 별도 state로 다시 만들지 않고 RHF가 제공하는 값을 쓰는가

> 상태 범위별 도구 선택은 `docs/architecture/state-management.md`.

---

## Accessibility  *(관련 변경이 있을 때만)*

점검 항목은 **`docs/convention/accessibility.md`를 직접 읽어서 그대로 적용한다.**
이 파일에 항목을 복제하지 않는다. 커스텀 인터랙티브 UI는 같은 문서의 WCAG 2.1 AA 목표를 기준으로 본다.

---

## Tests  *(관련 변경이 있을 때만)*

- [ ] 새로 추가된 동작 중 회귀 가능성이 있는 부분이 커버되는가
- [ ] 구현 상세가 아니라 동작을 검증하는가
- [ ] `skip` / `only` 가 남아있지 않은가

> 테스트 파일 위치·네이밍·러너는 `docs/convention/test.md`가 단일 출처.

## 코드 품질 (Toss Frontend Fundamentals)

가독성 · 예측 가능성 · 응집도 · 결합도를 **판단 프레임**으로 쓴다.
SKILL.md Step 8의 4가지 조건 중 하나에 해당할 때만 finding으로 올린다.

### 가독성
- [ ] 같이 실행되지 않는 분기가 한 함수·컴포넌트에 섞여 흐름을 따라가기 어려운가
- [ ] 복잡한 조건식에 의미 있는 이름이 없어 오해를 부르는가
- [ ] 중첩 삼항·깊은 분기로 수정 실수가 나기 쉬운가

### 예측 가능성
- [ ] 이름과 실제 부수 효과가 다른가 (조회처럼 보이는데 갱신한다 등)
- [ ] 같은 종류의 함수·훅인데 반환 형태가 제각각인가
- [ ] 다른 스코프의 이름과 겹쳐 잘못 참조하기 쉬운가

### 응집도
- [ ] 함께 바뀌는 코드가 멀리 떨어져 있어 한쪽만 고치기 쉬운가
- [ ] 폼 필드 정의·검증·초기값이 분산돼 있는가

### 결합도
- [ ] 한 곳을 바꾸면 **함께 고쳐야 할 위치가 불필요하게 늘어나는가**
- [ ] UI·상태·API 호출·데이터 변환이 한 곳에 섞여 회귀 가능성을 키우는가
- [ ] 트레이드오프 — 응집도가 깨질 위험이 있다면 중복을 남기는 편이 나을 수 있다

> "더 깔끔하게", "더 잘게 분리" 같은 취향 수준 지적은 등록하지 않는다.
> 컴포넌트 분리의 적정 수준 판단은 `docs/architecture/folder-structure.md`의 4가지 기준을 근거로 쓴다.
